# 维护经验

## 首次接入不能从示例名单直接开始部署

维护 Skill 面向已有后端，不能替代新用户的配置流程。首次接入应先发现真实的每日非监控任务，确认分类与朗读方式，再确认服务器，最后操作千问账号。任务清单、服务器方案和导出文件分别记录，导出不等于已经修改任务、部署服务或完成设备验证。私有策略路径必须进入实际运行配置；Linux 服务还需核对运行用户能读取该路径，不能因本地测试能读到 HOME 内文件就假定 systemd 也能读取。参见 [首次安装](setup.md) 与 [运行维护](operations.md)。

## 安装验收要区分源码目录与独立环境

构建验证可以把虚拟环境放在仓库的忽略目录内。仅判断安装模块是否位于仓库下，会把正常的 site-packages 误判成源码导入。安装验收应拒绝实际的 `briefing/` 源目录，并用 `python -I` 运行已安装包检查。验收需实际访问包内管理页面资源、加载来源策略并验证认证。

## 生成的环境文件按消费方格式处理

部署配置生成器输出的是 systemd EnvironmentFile 格式。文件使用 LF，值按该格式引用；不要用 shell 的 `source` 读取，也不要在日志里打印其内容。部署前先校验所有输入，保留已有角色凭据，避免重新生成时无意轮换或修改同目录的无关文件。

## 平台提示词不能证明每次重新取稿

要求 Skill 每轮调用工具，仍不能证明平台实际发出了请求。缓存更新后的验收须检查真实调用和返回内容；设备开始发声、整期播完与平台审核通过分别记录。相关限制集中维护在 [known-limitations.md](known-limitations.md)。
